## 4. Resiliencia y reconexión Api↔RaspberryPi↔WebClient (2026-07-06)

Feature diseñada con el flujo completo brainstorming → spec → plan → `subagent-driven-development`, ejecutada en una sola sesión intensiva el 2026-07-06 y **verificada empíricamente por el usuario** (pruebas manuales de caída/reconexión) antes del merge.

Problema que resolvía: si la Pi se caía, la Api no se enteraba (impidiendo reconectar); si la Api se caía, el WebClient no se enteraba (requería recargar la página).

- **Heartbeat ping/pong reutilizable** (`services/Api/src/robot/utils/heartbeat.py`), usado tanto en la conexión Api↔Pi como en Api↔Usuario.
- `ProxyStreamSource` (canal Api↔Pi) ahora propaga la desconexión física al pipe, sin perder mensajes ni corromper `CancelledError` en la carrera de `receive_data` (bug encontrado y corregido en revisión).
- `UserStreamSource` intercepta pongs y expone `send_control`, serializando todas las respuestas (incluidas las de error) bajo el mismo lock de escritura.
- `RobotConnectionRepository` soporta esperar la reconexión de un robot (`wait_for_robot_reconnect`), con la invariante documentada de un solo esperador por `robot_id`.
- El **pipe usuario↔robot sobrevive** a una caída y reconexión del robot (hasta 120s de espera) sin tumbar la sesión del usuario.
- `m2m.py` distingue **cierre limpio** (irrecuperable, tumba el pipe de inmediato) de **timeout de heartbeat** (recuperable, espera reconexión) — se corrigió un bug donde `websocket.iter_json()` de Starlette tragaba `WebSocketDisconnect` en silencio, haciendo la rama de cierre limpio inalcanzable.
- `WsStrategy` (lado Pi) responde heartbeat y detecta caída silenciosa de la Api, reconectando con backoff.
- WebClient (`useRobotSocket.ts`): reconexión automática con backoff y watchdog de heartbeat; `RobotControlPage.vue` muestra el estado de reconexión del robot al usuario, traduciendo correctamente los eventos de la Api (se corrigió un cast crudo de string que no traducía el estado real).
- Fix final (hallado en la revisión de rama completa): los comandos de usuario enviados **durante** la espera de reconexión del robot ahora se rechazan de inmediato con error JSON-RPC, en vez de intentar escribirse a un socket ya muerto y tumbar toda la sesión.

Spec: `docs/superpowers/specs/2026-07-06-resiliencia-reconexion-design.md`. Plan: `docs/superpowers/plans/2026-07-06-resiliencia-reconexion.md`.

## Conclusiones — mejoras funcionales respecto a la versión anterior

Comparado con `v0.1.0-alpha`, el sistema pasó de ser un prototipo funcional a una plataforma bastante más confiable y lista para operar en condiciones reales de laboratorio. En términos de lo que percibiría un usuario o un administrador, sin entrar en detalles de código:

- **El sistema ahora tolera caídas de conexión sin romperse.** Antes, si un robot se desconectaba (por ejemplo, se apagaba la Raspberry Pi o fallaba la red), el sistema no se enteraba: la sesión quedaba en un estado inconsistente y hacía falta intervención manual para volver a operar. Ahora la caída se detecta en segundos, se avisa al usuario, y si el robot vuelve a conectarse a tiempo (hasta 2 minutos) la sesión continúa sola, sin que el usuario tenga que hacer nada.
- **Si la reconexión no ocurre a tiempo, el usuario recibe un aviso claro** de que el robot no está disponible, en vez de quedarse con comandos que fallan en silencio o una pantalla que parece congelada.
- **Si el servidor central se cae, ya no hace falta recargar la página a mano.** Antes esa era la única forma de recuperar la conexión; ahora la aplicación web detecta la caída y se reconecta sola apenas el servidor vuelve a estar disponible.
- **Se simplificó el camino de comunicación entre el servidor y el robot**, eliminando un componente intermedio (RosBridge) que ya no era necesario. Menos piezas en el medio significa menos puntos donde algo puede fallar.
- **El software del robot ahora se puede instalar y actualizar en las Raspberry Pi de forma empaquetada** (mediante contenedores), en lugar de configurarse a mano paso a paso en cada máquina. Esto facilita sumar más robots al sistema y mantenerlos todos actualizados de manera consistente.
- **Se sumó la posibilidad de controlar el robot usando ROS 2** como alternativa interna, ampliando qué hardware o configuraciones puede soportar el sistema sin cambiar cómo se comunica hacia afuera.
- **Se reforzaron validaciones de seguridad** en la comunicación entre usuarios y robots que se habían relajado durante el trabajo de reestructuración interna.
- **El sistema quedó mucho mejor cubierto por pruebas automáticas** (de prácticamente ninguna a más de 140 entre los distintos componentes), lo que da mayor confianza de que cambios futuros no rompan lo que ya funciona.

En conjunto, la versión actual es notablemente más resiliente ante fallas de red o hardware — el escenario más común en un laboratorio remoto — y queda mejor preparada para sostenerse en producción sin supervisión constante.

## Gaps pendientes para v1.0.0

Pese a las mejoras descritas arriba, no calificaríamos a esta versión como "primera versión productiva" (v1.0.0) todavía. Hay dos gaps de seguridad que consideramos bloqueantes, y un par de gaps menores a anotar:

**Bloqueantes:**

- **Las rutas `/admin/robot` no tienen ninguna protección de autenticación.** No exigen sesión iniciada ni verifican que quien las llama sea un usuario con rol admin (`profe`), pese a que esa infraestructura (JWT, verificación de rol) ya existe y se usa en otras partes del sistema. En la práctica, cualquiera que conozca la URL podría aprobar, rechazar o crear robots sin loguearse. Esto ya está señalado como pendiente ("WIP") en la documentación interna del proyecto.
- **La conexión de producción no usa HTTPS/TLS** — el proxy solo escucha por el puerto 80 sin cifrado. Esto significa que credenciales de usuario, tokens de sesión y contraseñas de robot viajan en texto plano por la red. Es un riesgo aceptable en un entorno de desarrollo controlado, pero no para una versión etiquetada como productiva.

**Menores (no bloqueantes, pero pendientes):**

- No hay integración continua (CI/CD): los tests pasan localmente, pero nada los corre automáticamente al hacer push o abrir un PR.
- Quedan un par de validaciones sin terminar en el flujo de registro de usuarios (`auth.py`), marcadas explícitamente como TODO en el código.

**Recomendación:** cerrar los dos puntos de seguridad antes de etiquetar `v1.0.0` — son cambios acotados, no requieren rediseño. Si se quiere marcar este hito igual, una alternativa es taggear esta versión como `v0.2.0` o `v1.0.0-rc1`, dejando `v1.0.0` para cuando ambos gaps estén resueltos.
